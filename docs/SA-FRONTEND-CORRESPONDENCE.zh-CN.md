每条投影泳道都用同一个共享分词器读取其固定的 C#，并在这条 token 流上数花括号来切分方法体。这两个
函数位于每条锚点、每个精化泳道读取的每个字段之下：如果前端读取文件的方式与固定源码的含义不同，
那么每份下游回执仍然内部自洽，并且仍然是错的。这就是
`SOURCE_FRONTEND_AND_COMPILER_CORRESPONDENCE` 成为可信基础中最大单项的原因。

本文描述项目现在为这一项拥有什么，并且——至少同样重要——描述它不拥有什么。

## 构建了什么

第二个读取器 `formal/refinement/frontend_correspondence.py` 是一个字符状态机，与泳道使用的扫描器
不共享任何代码：它一次一个字符地遍历文件，通过扫描到闭合引号来保持字面量不透明，并在得到的片段上
数花括号。前端没有被复制进去。从七个本应共享一个读取器的泳道模块中读出的，是命名它的那条
*声明*；在比较任何东西之前，先要求这七个模块命名同一个：

| 读取器 | 模块 | 状态 |
| --- | --- | --- |
| `csharp_tokens.TOKENIZER` | `abi_admission_source`, `contract_handoff_source`, `entry_dispatch_source`, `exception_identity_source`, `interop_convert_source`, `interop_fee_source`, `syscall_dispatch_source` | 一条声明，运行时验证，然后加载并执行 |
| 私有表 | `gas_proofs`, `runtime_collection_source`, `runtime_source` | 在回执中具名，不合并 |

后三个是具名而不是被悄悄当作同一个读取器。它们的泳道读取更窄的字符集，因此位于这些面之外；这是
测试装置的适用范围限制，不是那些表的属性，回执也说明它覆盖哪些模块、不覆盖哪些模块。

读一条声明比读一张表弱，这种替换是刻意的：算法不再是一个可被测试装置重新解释的字符串，因此编译器
面度量的是算法本身，而声明普查只度量七个泳道是否仍然就“使用哪个读取器”达成一致。两个事实都
需要，且互不替代。

## 逐级增强的五个面

这项工作产生的第一件事，是关于那个显而易见比较的负面结果。连接 token 就是拼接，所以

```
normalize("a == b")  ==  normalize("a = =b")  ==  "a==b"
```

因此规范化文本相等只证明一件事：两个读取器丢弃了相同的字符，也就是空白与注释，别无其他。它看不见
画错位置的边界。所以测试装置比较五个面，并说明每个面是什么：

| 面 | 它能看见什么 | 实测（门禁 29） |
| --- | --- | --- |
| `normalize` | 被丢弃字符的集合 | 22 个文件，0 处不匹配 |
| `tokens` | 画错位置的边界 | 19,486 个 token，0 处不匹配 |
| `bodies` | 结束方法的花括号 | 109 个方法，0 处不匹配 |
| `anchors` | 泳道命名的片段是否以相同方式被接受并连接 | 1,291 个片段，0 处分歧 |
| `needles` | 同上，针对投影代码读字段所用的短字面量 | 648 个片段，0 处分歧 |

方法体面是泳道真正依赖的面，每个方法的头部由独立的 span 索引逐字从文件中取出，因此两个读取器收到
相同的字节，而不是相同的意图。

第四个面针对泳道实际对文本做的事。每条泳道声明若干锚点——从固定源码中引出的语句片段——并要求每个
锚点在读取字段之前恰好出现一次。如果两个读取器以不同方式连接一个片段，锚点就会落到别处，它之后的
每个字段都会从错误位置读出。因此测试装置解析九个泳道模块（只解析，从不导入：导入一个可能触发下载），
取出每个至少十个字符的字符串常量：1,291 个片段。两个读取器接受其中 1,189 个，拒绝 102 个，且没有
一方接受另一方拒绝的——分歧为零。被接受的片段中有 397 个出现在语料中，其中 378 个恰好出现一次，
这正是泳道在信任锚点之前所要求的唯一性。

被拒绝的 102 个片段是那个数字中有意思的一半。它们被*两个*读取器同时拒绝，因为它们含有两个读取器
都没有的字符——大多是反斜杠，来自那个保存正则表达式的泳道模块。双方都拒绝不是关于含义的一致，而是
关于作用域的一致，测试装置把它单独计数，而不是折入成功数。

两次独立测量，同一读取器，不同语料：

| 语料 | 文件 | Token | 方法 | 不匹配 |
| --- | --- | --- | --- | --- |
| 本地保留的六个泳道镜像 | 26 | 20,151 | 117 | 0 |
| 门禁 28 留下的七个 `source` 目录 | 22 | 19,486 | 109 | 0 |

### 锚点面曾经的地板

十个字符是一个洞。泳道读字段不是靠引用一句话；它用投影代码里实际存在的字面量去读——`if(verify)`、
`returnnull;`、`_=x.ToDictionary(...)`——然后问 `needle in text` 或 `text.count(needle) == 1`。
一个七个字符的短针仍然决定泳道认为自己看到的是哪个文件的哪个区域，而锚点面完全看不见它。

于是有了第九个模块，以相同方式读取，且没有长度地板：泳道模块*函数体*内的每个非空字符串常量，减去
八个属于管道而非投影的函数——`body`、`canonical`、`download_pinned`、`mirror_source`、`normalize`、
`require`、`sha`、`source_url`，它们固定 URL、哈希字节、查找名称或切分方法体。被排除的名称打印在
回执中，且有一个单元测试在该名称不再存在时拒绝该集合，因为一次重命名不得悄悄放宽过滤器。

这就是 **648 个片段，其中 133 个短于锚点地板**。每个片段都被问与锚点相同的三个问题，外加只有短针
才需要的第四个：两个读取器在每个语料文件的每个文件里找到它的次数是否相同？584 个可读，64 个被两个
读取器同时拒绝——这些数字取决于片段而不是语料，因此两个语料报告的结果相同。200 个针出现在语料中
（`168` 个在 26 文件本地镜像中恰好一次，`165` 个在门禁 29 留下的 22 个文件中恰好一次）。没有一方
接受另一方拒绝的片段，没有片段被以不同方式连接，没有片段被以不同方式计数：**两次运行中三个问题
上的分歧都为零。**

没有对照的零什么也不是。对照是一个在每个长片段上都正确、在短片段上却错误的前端：它从任何短于十个
字符的内容中丢弃 `(`。锚点面报告零问题——它从不看那么小——而短针面在第一个针上报告一处连接分歧。
这就是 `test_a_defect_in_a_short_needle_is_invisible_to_the_anchor_face`，也是这个面存在的原因。

对它所增加之物有一个诚实的界。如果 token 面在一个文件上一致，那么该文件上的每次子串查找也一致，
所以短针面对于整文件没有说出新东西——计数问题已被做过的工作蕴含。它增加的是片段一侧：133 个短字符串，
位于每条泳道投影的顶部附近，运行中此前没有任何其他东西看过它们。门禁还拒绝一个找不到任何针的短针面，
因为在空问题上的一致不是一致。

## 语料没有携带的东西

普查记录语料实际拼出了哪些 token 类，因为没有任何文件包含的运算符不能作为任何证据。表中的每个运算符
都至少被拼出一次；最稀有的是 `--`（1 次）、`%`（3 次）、`^`（3 次）、`~`（3 次）、`&`（4 次）、
`<=`（4 次）、`++`（7 次）。这部分确实被演练了。

方法体面存在所针对的那个危险则没有。一个数花括号却不尊重字面量的读取器在这个语料上仍然会一致，
因为字面量内部唯一的花括号是插值字符串孔洞，它们是配对的，因而相互抵消。语料中有两个字面量含有
不配对的花括号，且都来自同一个真实构造：

```csharp
return $"[{string.Join(", ", _innerList.Select(p => $"{p.Type}({p})"))}]";
```

那一行是上游 `neo-vm` 在 `004cd6070a940405818d9357638277dd44407e2e` 的
`src/Neo.VM/EvaluationStack.cs`——镜像字节与直接从仓库取到的文件哈希相同，都是 `7190a363…`，所以
这个怪现象不是镜像造成的。C# 把插值孔洞内部的引号词法分析为嵌套字符串字面量；那个时代的两个读取器
都在内层引号处切分字面量，而且切在完全相同的位置。

本文早先的草稿说投影不受影响，“因为切分的字面量保留了每个字符”。那是错的，C# 词法器证明了这一点。
表把 `string.Join(", ", …)` 读成：`$"[{string.Join("` 结束第一个字面量，分隔符自己的 `,` 作为
运算符被发出，其内容空格作为空白被丢弃，分隔符的闭合引号打开下一个字面量。连接后的文本比源码短一个
字节，而两个读取器在那个更短的文本上一致。两个读取器之间的一致看不见这一点；只有两者之外的权威
才能看见。

## C# 词法器本身

于是有了第三个读取器，而且它不是我们的：来自 Microsoft Roslyn 的 `SyntaxFactory.ParseTokens`，
在同一语料上运行，丢弃全部 trivia，并按泳道连接 token 文本的方式连接。由此得到两个事实，第二个才是
让这一项可度量而不是自指的东西：

在门禁自己的语料上，同样的比较在彼时（门禁 24）读到：

| 比较 | 结果 |
| --- | --- |
| 整文件连接，正则前端 vs C# 词法器 | 比较 22 个文件，20 个相同，2 个不同 |
| 前端找到、且 C# 词法器也找到的泳道锚点 | 397/397，0 处分歧 |

那个 dump 不是新工具。`formal/refinement/export` 已经携带 Roslyn，每次门禁运行都会重建它，其编译器
包按哈希审计，因此为它增加了一个第二模式：

```sh
dotnet export/bin/Debug/net10.0/RefinementExport.dll --token-dump /path/lexer-tokens.json
```

门禁在泳道结束之后调用它，放在对应回执旁边。没有新项目、没有新包、没有新的网络依赖。

两个不同的文件被识别出来，且都不是谜：

- `vm-stack.cs` — 上面的插值字符串孔洞，丢失一个内容字符。正则表无法建模插值，因为孔洞需要嵌套，
  而共享表是一条单一正则表达式。
- `vm-engine.cs` — 前端读到而编译器没读的 214 个字符，因为 `strip_directives` 移除了 `#if VMPERF`
  行却保留了被禁用的方法体，而词法器丢弃整个区域。

两者都是前端的真实缺陷，且都在泳道命名的每个片段之外：泳道定位的全部 397 个锚点都被 C# 词法器以
相同计数定位，在两个被测语料上都是如此。这就是本文划的线——前端必须在泳道读取的一切上与编译器一致，
它确实一致；泳道不读的文本也不得掩盖缺陷，这就是为什么两者都被修复而不只是被度量。

在存在期间，两个缺陷都没有被原谅：测试装置携带了一个编译器确认的读取器，因此各自的规模是测量而
不是估计，“我们在某处丢了一个字符”与“我们在泳道不读的文本里丢了一个字符”之间的区别，是回执里的
一个数字。

## 编译器确认的读取器

`strip_directives` 丢弃 `#` 行并保留方法体，这是一个*没有*条件语义的读取器被迫采用的读法。编译器
不被迫如此。因此测试装置携带了第二个读取器——`strict_spans` 与 `active_text`——它把插值字面量读作
一个 token、孔洞在其中，并求值指令条件而不是丢弃它们。它不是泳道使用的读取器；它是用来评判泳道的
读取器，而且只有在它在所有地方都复现词法器之后，才被允许评判：

| 比较 | 结果（门禁 27） | 结果（门禁 28） | 结果（门禁 29） |
| --- | --- | --- | --- |
| 严格读取器 vs C# 词法器，连接文本 | 22/22 相同 | 22/22 相同 | 22/22 相同 |
| 前端 vs C# 词法器，连接文本 | 21/22 相同，1 个不同 | **22/22 相同** | **22/22 相同** |
| 泳道锚点，由严格读取器读取 | 检查 397 个，0 处分歧 | 检查 397 个，0 处分歧 | 检查 397 个，0 处分歧 |

门禁 29 是同一语料加上第七个面，且没有移动任何其他数字：22 个文件、19,486 个 token、109 个方法、
1,291 个锚点、每个面 0 处分歧、`knownGaps` 为空，且回执自身的哈希可由其内容重新计算。

第一行是第二行得以成立的前提。前两行合起来是发现的形状：存在一个与编译器连接完全相同内容的读取器，
而前端不是它，起初在两个具名文件上如此——随后在一个文件上如此。现在两行一致，这就是 `knownGaps`
的前端列为空的原因。

每个差异的原因都是计算出来的，不是猜的——每项补救都单独应用并与词法器比较，因此需要两项的文件说
`both`，两项都不需要的文件说 `unclassified`，而不是被强行归入某一类。既然字符串规则不再有争议，
只剩一项补救可切换：指令是被求值还是仅被丢弃，而分类器只在两种读法确实不同时才归咎于它：

| 文件（门禁 27） | 字节 | 原因 |
| --- | --- | --- |
| `vm-stack.cs` | 前端 4,000 / 词法器 4,001，首个差异在 3,950 | `interpolation-hole` |
| `vm-engine.cs` | 前端 4,004 / 词法器 3,790，首个差异在 1,615 | `disabled-region` |

两个缺陷也被保留为可执行形式，因此回执携带的是复现器而不是故事，且门禁要求两者一致：

| 复现器 | 前端连接结果 | 编译器连接结果 |
| --- | --- | --- |
| `$"[{string.Join(", ", items)}]"` | `$"[{string.Join(", ", items)}]"` | 相同 |
| `#if VMPERF` / `Hidden();` / `#endif` / `Visible();` | `Visible();` | 相同 |

### 曾经非零的那个数字

有一个具名片段确实移动了：`CurrentContext` 在前端对 `vm-engine.cs` 的读取中出现 13 次，在编译器中
出现 10 次，因为被禁用的 `#if VMPERF` 块提到了它三次。它连同两个计数一起在 `knownGaps` 下报告，
并被报告为*歧义*而不是移动的位置——这个区别正是关键，因为出现不止一次的片段什么也定位不了。
`anchorsAffected` 为 1，`anchorsAffectedUnique` 为 0，而门禁强制的规则是：在任一侧唯一的片段才是
移动了的位置。

没有泳道单独命名 `CurrentContext`；它出现在更长的锚点中，例如
`ExecutionContextStatestate=CurrentContext!.GetState<ExecutionContextState>();`，而那些从未受影响。
正确读取该区域之后计数一致，两个数字都是 0。

### 两者中的第一个，已修复

`#if` 那一半可以修，而且已经修了。`strip_directives`——两个泳道携带、测试装置镜像的名称——现在只
存在一处，位于 `csharp_directives.py`，它求值条件，而不是丢弃该行并保留方法体。泳道不导入测试装置：
度量仪器不得是被度量之物，因此规则有两份副本，并有一个测试要求它们在电池用例与整个语料上一致。

这是安全的证明在编辑之前就已给出，而且来自泳道自己的投影，而不是文本统计：

| 泳道 | `program`（主张） | `methods`（记录的方法体） |
| --- | --- | --- |
| `exception_identity` | 相同 | `executeNext` 749 → 577，`onFaultVm` 64 → 22 |
| `abi_admission` | 相同 | 相同（其文件中没有条件区域） |

两个变化的方法体都是 `VMPERF` 跟踪区域，它们只打印、不赋值任何状态——这正是没有字段移动的原因，
也正是必须正确而非方便地读取该文本的原因。`sourceHashes` 仍然哈希原始字节，因此固定值未被触动。

改动之后，前端在 26 个文件中连接相同的有 25 个，`knownGaps` 中只剩一个文件而不是两个，
`anchorsAffected` 为 0。缺口列表是门禁中的冻结常量，因此退役一个缺口是一次带注释的刻意编辑；
`vm-stack.cs` 中的插值孔洞保留，因为它需要一个跟踪嵌套的词法器，而不是一个求值条件的读取器。

### 第二个，也已修复

`vm-stack.cs` 是更难的一半，原因是结构性的：共享分词器是一条单一正则表达式，而孔洞是可以包含引号的
表达式。修复它意味着在全部七个规范模块中替换那条表达式，而每个泳道都用它切分方法体——因此它在
动手之前就被度量，而不是之后。

`csharp_tokens.py` 就是那个扫描器，度量分三部分。第一，token 流：在固定语料上，
`25 of 26 files are token-identical`，四个带指令的文件被双方拒绝（泳道先读指令），恰好一个不同——
`vm-stack.cs`，其中 14 个 token 变成 1 个。

第二，投影，这才是真正重要的。每条泳道在同一镜像上运行两次——一次用自己的表，一次把 `TOKEN` 重新
绑定到扫描器——并把两份报告作为规范 JSON 比较：

| 泳道 | `project_production` | `project_captured` | 应用的控制 | 相同 |
| --- | --- | --- | --- | --- |
| `abi_admission` | 相同 | 相同 | 54 | 是 |
| `contract_handoff` | 相同 | 相同 | 42 | 是 |
| `entry_dispatch` | 相同 | 相同 | 24 | 是 |
| `exception_identity` | 相同 | 相同 | 32 | 是 |
| `interop_convert` | 相同 | 相同 | 36 | 是 |
| `interop_fee` | 相同 | 相同 | 32 | 是 |
| `syscall_dispatch` | 相同 | 相同 | 26 | 是 |

合计 246 个控制，判定全部相同，而一条泳道拒绝的 12 个控制，两种方式下都被完全相同地拒绝。第三，
文件层面的影响半径：固定 `EvaluationStack.cs` 的三条泳道中，没有一条从中取出方法体，而
`sliced_files()` 正是重新计算这一点的地方：

| 问题 | 答案 |
| --- | --- |
| 固定 `EvaluationStack.cs` 的泳道 | 三条：`contract_handoff`、`entry_dispatch`、`syscall_dispatch` |
| 从中取出整个方法体的泳道 | 无 |
| 读取它的泳道，以及如何读 | `entry_dispatch`，对原始字节做 `text.count(needle) == 1` |

最后一行就是该文件的 token 流从来不是字段承重结构的原因：短针计数读的是文件字节，不是它的 token。
门禁从模块重新计算该主张，而不是相信本段文字：

```python
require(not frontend_receipt['knownGaps']['slicedGaps'], ...)
```

`slicedGaps` 通过解析泳道模块中的 `SOURCES`、`SIGNATURES` 与 `body()` 切分器来计算，因此一旦某条
泳道开始切分该文件它就会移动。没有切分器的模块在 `lanesWithoutBodySlicer` 中具名，而不是被计为已
检查，因此空结果不可能成为静默跳过。

### 门禁现在要求什么

- 严格读取器在**每个**文件上复现 C# 词法器，而不只是方便的那些；
- 前端也在每个文件上复现它——那一行曾经是 `25 of 26`，现在是 `26 of 26`；
- `anchorsAffectedUnique` 为零；
- 短针面不为空：它必须报告片段、可读片段与低于锚点地板的片段，否则一次什么都没比较的运行也会通过；
- 没有缺口落在任何泳道切分方法体的文件上；
- `knownGaps` 中的文件集合等于 `KNOWN_FRONT_END_GAPS`，而它现在**为空**。

最后一条在两个方向上都是冻结的，且已被手工清空过两次。一次运行若增加缺口，就是有了新缺陷，必须
说出来；一次运行若闭合缺口，就是改进了前端，而编辑那个列表正是记录改进的方式。一个可以悄悄缩短的
固定列表不是固定的——这正是扫描器落地时不允许它自行缩短的原因。

其余危险由一个自测承担：十三项检查，其中七项在构造的代码片段上确认独立读取器，六项确认字面量盲
读取器在盲读取器能看出差异的片段上得到*不同*答案。没有后一半，零分歧的运行就无法与什么都没比较的
测试装置区分开。

## 这项工作逼出的三个事实

**Token 类与边界。** 泳道消费连接后的字符串，而不是 token 列表。这使 `normalize` 相等成为它们需要
的确切性质，也使 token 面严格强于必要——这是犯错时正确的方向，但必须说明，因为一个读取器可以在
三个面上都一致，却仍然不是 C# 解析器。

**一个读取器，七条声明。** 前端过去以一条正则表达式的七份字面副本存在；现在它是一个扫描器，七个
模块各用一行命名它。`canonical_reader()` 读取全部七条声明，若它们不一致就拒绝比较任何东西，然后
加载并运行它们命名的读取器。悄悄停止共享它的泳道会让对应检查失败，而不是静默地以不同方式投影。

**是门禁失败，不是警告。** 回执在每次门禁运行时从泳道刚下载的固定 C# 重新计算，不匹配即让运行失败。
检查是 `correspondence.agrees(frontend_receipt)`；不存在记录分歧后继续的路径。

**度量必须在修复之后仍然存在。** 移除缺陷并没有移除这些面：`normalize`、`tokens`、`bodies`、
`anchors` 与 `needles` 仍把前端与一个独立编写的读取器比较，`lexer`、`strict` 仍把它与 Microsoft 的
读取器比较。消失的是借口那一列。一个只懂得说“这是预期的”的测试装置，在没有任何东西可预期之后
将无话可说——这就是缺口列表是冻结常量而不是过滤器的原因。

## 另一半本来就在那里

这一项的名字连接了两件事，值得把它们分开，因为它们由不同机制以不同强度确立：

| 腿 | 由什么确立 | 强度 |
| --- | --- | --- |
| C# 项目 -> NEF 字节 | `formal/refinement/export` 用固定的 NCCS 3.9.1 重新编译 `contracts/custom/SmartAccount.csproj`，并要求 `File.ReadAllBytes(compiled).SequenceEqual(pinnedNefBytes)`，外加对 manifest 的 `JsonNode.DeepEquals` | 每次门禁运行的字节身份 |
| C# 文本 -> 泳道读取的内容 | 本测试装置 | 两个独立读取器在实测语料上的一致 |
| ABI -> 真实引擎派发的内容 | `export --abi-dispatch` 加 `abi_dispatch.py` | 109 个条目中 107 个派发到声明偏移，两个引擎入口点按名称拒绝 |
| C# 语义 -> VM 语义 | 仍只有派发路径之外的空无，本文不主张任何东西 | 开放 |

第一条腿比第二条强，且早于它。`verify.py` 构建 `export/RefinementExport.csproj` 并在门禁的 `base`
步骤中运行它，因此每次调用都从源码重新编译合约并拒绝一个字节的差异；编译器自身的程序集字节与已
审计的 `.nupkg` 条目比较，包哈希是导出器中的常量。因此投影泳道从不需要相信文本与工件相关——导出器
会检查。

缺失的是中间那条腿。泳道用分词器与花括号计数器读取文本，而没有任何东西把这种读取与任何东西核对。
这就是本测试装置增加的内容，也是唯一一条检查是一致而非身份的腿。

## 由真实引擎运行的工件

上面一切都是关于文本的。它们都没有说编译后的字节就是泳道从 C# 读出的含义，这就是这一信任项的中间
腿过去只是“关于文本的一致”、而第三条腿是“空无”的原因。`ACTUAL_VM_APPLICATION_ENGINE_ABI_DISPATCH`
就是那第三条腿，而它的一个部分现在是被度量而不是被假设的。

一个新的导出器模式——`--abi-dispatch FILE --nef … --manifest …`——把固定的 NEF 部署进真实的
`ApplicationEngine`（Neo 3.9.1，编译器随附的程序集：`Neo.dll`、`Neo.VM.dll`、
`Neo.SmartContract.Testing.dll`），然后按名称以 manifest 声明的元数调用每个 ABI 方法，单步执行该
调用，并为每个方法记录：

- 引擎进入的偏移（`firstIps[2]`，被调用者的第一条指令）；
- 声明偏移处的指令是否真的执行过；
- 最终状态与故障消息；
- 合约按顺序到达的系统调用，由 interop 表解析。

随后 `abi_dispatch.py` 对那次度量问六个问题，且只问六个：dump 是否恰好覆盖 manifest 的方法（计数
相同、name/arity 集合相同）；对每个不是引擎入口点的方法，进入偏移是否等于声明偏移；声明偏移处的
指令是否真的运行；`_deploy` 与 `_initialize`——引擎自行调用并拒绝按名称派发——是否被拒绝，这被记录
为关于引擎的事实而不是借口；调用留在栈上的值是否具有 manifest 声明的形状；以及——第六个，在前五个
闭合之后添加——manifest *没有*描述的调用是否在边界被拒绝，或落在 manifest 说它们应落的位置。那个
第六个问题就是下一节。

| 问题 | 固定工件上的结果（门禁 32） |
| --- | --- |
| 被度量的方法 | 100/100，name/arity 与 manifest 匹配 |
| 派发到声明偏移 | 98 |
| 按名称拒绝的引擎入口点 | 2（`_deploy`、`_initialize`） |
| 声明偏移被执行 | 已派发的 98/98 |
| 以 `HALT` / `FAULT` 结束 | 39 / 61——故障是零参数故障，不是派发失败 |
| 返回形状匹配声明类型 | 39/39 个完成的调用，0 处不匹配 |
| 观察到的系统调用 | 355，每一个都由 interop 表解析 |
| 惰性 initializer 调用 | 98（编译器的静态初始化守卫从每个方法内部运行 `_initialize`） |

当前工件在 2026-11-17 重新度量：109/109 个方法与 manifest 匹配，107 个进入其声明偏移，`_deploy` 与
`_initialize` 是两个被拒绝的名称，42 个完成的调用匹配其声明返回形状，67 个因零参数而故障。回执记录
399 个已解析系统调用与
`receiptSha256: f75e1226fd445b31112003f84f609486cbfbb9d92c8eacc902a72642650a046c`；其十七项
自检全部拒绝了各自的变异。对应的足迹是 30,678 字节 / 10,594 条指令、238 个区间、362 个进入的字节
方法全在 996 方法的静态闭包内、634 个可达但未进入的方法、零个未知、无主或闭包外执行偏移——887 个
外来 script 偏移单独计数，不计为自有合约指令——以及
`receiptSha256: 20833d6456d0cd4ebba05bd0b5356e2e834960063a4f9e0fa2487671baf2d847`。

故障计数是那张表中诚实的一部分。一个以 `0`/`null` 参数发起的调用不是合约为其编写的调用，因此历史
门禁 32 工件中有 61 个方法中止，当前工件中有 67 个；回执确立的是*引擎去了哪里*，而不是方法成功了。
一个要求 `HALT` 的面将是一个要求无人拥有的 fixture 的面。

返回形状规则是被度量的，不是被规定的，而初稿把它弄错了。`System.Contract.Call` 无论被调用者结果
是什么都会把它压栈，因此对 `Void` 方法的具名调用留下**一个 Null 项**，而不是零个：两个完成的 void
方法（`cancelUpdate`、`cancelAdminTransfer`）表明了这一点，规则现在把 `Void -> Any` 映射。映射的
其余部分是 manifest 自己的词汇与栈的词汇对照：`Hash160` 必须是 20 字节 `ByteString`，`Hash256` 32，
`PublicKey` 33，`Signature` 64，`Boolean` 是 `Boolean`，`Integer` 是 `Integer`，
`ByteArray`/`String` 是 `ByteString`。故障必须不留下任何东西——故障旁边出现结果将意味着度量描述的
是另一次运行——而这对全部 61 个都成立。

有两个声明类型**不被这个面覆盖**，回执如实说明而不是把它们计为已测试：`Any` 与 `Array` 只由在零
参数上故障的方法声明（`executeUserOp`、`registerAccounts`、批量入口），因此它们的映射从未被应用。
`declaredTypesUnexercised: ["Any", "Array"]` 是读者在相信返回面覆盖一切之前应该看的那一行。再下一节
就是闭合它的地方，门禁在两个面的*并集*覆盖每个声明类型之前拒绝通过。

null 返回是 manifest 无法表达的唯一情况。Neo 的 ABI 没有可空性，因此
`object[]? GetPendingVerifierUpdate(...)` 仍声明 `Array`，而没有待处理更新的调用回答 null。在那里
要求一个值会让正确的合约失败；把 null 计为匹配会让未测试的映射看起来已测试。因此规则是三值的：
声明类型的值是匹配，声明引用类型处的 null 被允许并计入 `nullReturns` 而不标记该类型已演练，声明
*值*类型处的 null 是不匹配。这是被度量的，不是被规定的——已注册账户上的 `getPendingVerifierUpdate`
正是形状规则第一次遇到 null 的地方。

每次调用都会对 dump 运行十个变异——声明偏移被移动、派发落到别处、某个入口从未运行、缺失方法、
声称可调用的保留入口点、引擎不认识的系统调用、绑定到另一份 manifest 的 dump、manifest 未声明类型
的返回值、声明了值却什么都不返回的完成调用，以及在承诺值类型处出现的 null。另有七个变异边界探针，
见下文。每一个都必须被抓住，因此零问题的运行不能与什么都没比较的面混淆。

这仍未确立：带真实参数的调用按预期行事、`contracts/` 中的 C# 与操作码行为一致，或任何关于回滚、
gas 或异常身份的东西。它说的是引擎的派发与返回形状在这个工件上与 manifest 一致，比“源码与编译器
一致”低一层，比“实现正确”低两层。形状匹配不是值匹配：`getContractAdmin` 返回 20 字节，并不能说明
是哪 20 字节。

### 派发规则的另一半

上面每次度量描述的都是与 manifest **匹配**的调用。一条派发规则有两半，第二半——引擎对 manifest 未
描述的调用做什么——此前未被度量，这就是一个面最终只对容易方向表示一致的原因。同一个导出器模式现在
还运行 408 个任何 manifest 都不会接受的探针，并记录发生了什么，而不判定本应发生什么：

| 探针 | 数量 | 引擎做了什么 |
| --- | --- | --- |
| 派发面所做的调用，重跑 | 109 | 107 个进入声明偏移；2 个引擎入口点被拒绝 |
| 该名称没有任何重载声明的参数个数 | 202 | 202 个在被调用者帧存在之前拒绝，0 个进入 |
| *兄弟*重载声明的参数个数 | 2 | 2 个进入——`finalizeEscape/2` 在 11096，`finalizeEscape/3` 在 11108 |
| 没有方法声明的名称 | 1 | 拒绝 |
| manifest 说不可能到达的形状的参数 | 94 | 94 个进入；87 个在内部故障，7 个回答 |

拒绝不是传说：每一个都携带引擎自己的消息，而面把它固定下来。没有任何重载拥有的参数个数返回为
`Method "computeRegistrationAccountId" with 4 parameter(s) doesn't exist in the contract 0x…`，
由 `ContractManagement` 在本合约任何指令运行之前抛出——探针记录 `entered: false` 与低几十的步数，
而对照是两百多步。以下划线开头的名称在更早一步按名称被拒绝，
`Method name '_deploy' cannot start with underscore`，这就是两个保留入口点的元数探针携带那条文本
而不是另一条的原因。两条不同消息、两项不同检查，都在被调用者之前——而不携带任何一条的拒绝是面要
报告的问题，而不是归档的度量。

两个重载探针是正向的一半。`finalizeEscape` 被声明两次，元数为 2 与 3，对每个计数的调用进入不同
偏移；仅名称无法选择，仅元数也无法。这是该工件中唯一能表明 manifest 声明的 (name, arity) 对就是
引擎派发所用对的地方。

94 个形状错误的参数是发现，而它们不是这个面初稿所预期的。**没有一个在边界被拒绝。** 在声明
`Hash160`、`ByteString` 或 `Integer` 的地方传入空数组，仍然到达被调用者：其中 87 个调用随后在合约
*内部*失败——38 个在 `StackItem.GetInteger` 处报 `Specified cast is not valid`，其余在该入口自己的
中止处（`Account id required`、`Account not found`、`Platform registrar not set` 等）——另有 7 个
正常回答：两个 `supports*` 谓词、`computeArgsHash`（它哈希了交给它的空数组而不是拒绝它），以及
场景层已经度量过返回 `false` 的四个 `can*` 守卫。因此在这个引擎中，manifest 的参数类型是给工具的
文档，不是准入规则。回执记录 `shapeEnforcedAtBoundary: false`，并在边界块自己的主张中记录
`boundaryRefusalsAreStructural: true`；发明 ABI 看起来应有的那条规则将是错误类型的一致，面也会因此
让一个正确工件失败。在引擎*确实*拒绝某种形状的地方，同一个计数器转为 true 而运行仍然通过——该标志
报告被度量的是哪个引擎，而不是合约是否良好。

七个变异防止这变成自我庆贺：一个探针缺失、一个元数拒绝声称已进入、一个元数探针被重新标记为
重载、一个重载被送到错误兄弟、一个拒绝的原因是被调用者的（`ABORTMSG`）而不是边界的、一个形状错误
的参数落到别处，以及一个因无人命名的原因被拒绝。探针集合本身从 manifest 重新计算——每个方法的计数
减一与加一，减去兄弟声明的计数，加上每个非 `Any` 首参数一个类型探针，再加一个未声明名称——因此一个
悄悄停止发出探针的导出器是分歧，而不是更小的度量。门禁 37 是携带它的运行，回执哈希说明移动了什么：
派发面从 `24aac44d…` 变为 `f9429279…`，而足迹、词法器面与全部四份场景回执逐字节未变。

### 派发之下的一层

一个落在正确偏移上的派发器，对其落到的 方法体什么也没说。合约可以完美派发，然后运行其模型没有
计入的指令，而上面每个问题仍回答“一致”。

`dispatch_footprint.py` 从另一侧闭合这个缺口。导出器现在还按方法写出**引擎在合约内部执行的指令偏移
集合**、它所对照的 script 字节，以及它进入的每个帧深度的 script 哈希。第二个读取器用本仓库自己的
独立解码器（`nef_decode.py`，Neo.VM 3.10.1 表）解码那些字节，并把结果与 `entrypoint_inventory` 的
静态模型对照：对每个入口点，其依赖图可达的字节方法集合，加上 initializer 的闭包。

| 问题 | 含义 | 固定工件上的结果（门禁 31，门禁 32 复认） |
| --- | --- | --- |
| 字节 | dump 的 script 解码到两份文档都主张的 sha256 | 25,620 字节，8,833 条指令 |
| 边界 | 每个执行偏移都是该 script 的指令起点 | 1,661 个不同偏移中 0 个未知 |
| 区间 | 清单的 200 个字节区间划分该 script，每个执行偏移恰好有一个所有者 | 无洞、无重叠、0 个无主 |
| 可达 | 引擎进入的字节方法位于该入口静态图可达的方法之中 | 315 个在闭包内，0 个在外 |

在 98 个已派发调用中，引擎进入 315 个字节方法——被多个调用进入的 helper 每次调用计一次——且每一个
都在该入口的闭包中。静态闭包共列出 996 个成员，因此本次运行有 634 个可达但未进入。这个数字被报告，
且刻意**不是**失败：`reachable` 是一个可能集，它列出某条路径可能到达的每个方法，而零参数调用只走
一条路径。要求相等的面将是在索要无人拥有的 fixture，更糟的是，会报告一个不存在的分歧。必须成立的
方向是另一个，而它成立。

有两个细节值得点名，因为初稿把两者都弄错了：

- 帧归属由**运行中 script 的哈希**决定，而不是由栈深度决定。原生合约调用会压入自己的上下文，其
  指令指针在另一份 script 中从零编号，因此深度规则可能把本合约从未运行的偏移记到它头上。按哈希
  过滤也把在其他 script 中执行的 887 个偏移排除在比较之外，而不是悄悄混入。
- “声明入口运行了”是针对**偏移**测试，而不是针对所属字节区间。所有者集合说“这个方法运行了”；这里
  的问题是“manifest 指向的偏移运行了”。一个从方法体第三条指令开始的足迹对所有者集合测试不可区分，
  却是不同的主张。

每次调用运行八个变异，且两侧都被刻意变异：只不信任 dump 的面会放过一个忘记了引擎明显进入过的方法
的闭包。在手头这对数据上无法构建的变异被记录为 **skipped** 并让运行失败，因为一个悄悄缩小到仍然
适配的自测会认证它没有检查的输入。回执还记录具有逐字节相同足迹的最大方法组；在固定工件上是 1，
因此这是 107 条轨迹，而不是一条轨迹被重新标记 107 次。

足迹增加了什么、没有增加什么：它说的是一个参数全为零的调用*进入了哪些指令*。它对那些指令计算的
值什么也没说，因此它不能把 `FAULT` 变成通过，也不能把通过变成证明。`fullImplementationVerified`
保持 `false`。

### 足迹之下的一层

上面两层都以元数匹配的零值调用每个入口一次。这使它们可在全部 109 个入口之间比较，也是它们的极限。
在下文引用的历史门禁 32 工件上，98 个已派发调用中有 61 个在其第一个参数守卫处停止；当前门禁必须
重新度量该计数，而不是继承它。一个拒绝零值的方法体与一个能工作的方法体，对只发送零值的面不可区分。

`abi_scenario.py` 改为发送值。一个场景文件——受复核的输入，其 sha256 随回执传递——声明一个有序列
调用：方法、字面参数、具名签名者、运行时的区块时间、调用落在的合约、期望的结束方式，以及结果应
等于的较早参数。导出器把固定 NEF 部署进同一引擎，以声明账户签名，并在一个存储快照上按序运行调用。
写入与其后的读取都被记录，这才使消费者能把“引擎回答了什么”与“写入了什么”对照，而不是把引擎与
它自己比较。

八个问题，每一个都有失败的方式：

- **编码。** 帧在这里仅由场景重建——参数逆序压栈（PACK 从栈顶填充索引 0）、每个字节串用
  `PUSHDATA1` 因为 Neo N3 没有 `PUSHBYTES` 操作码、`604800` 用补齐到四字节的 `PUSHINT32`，系统调用
  操作数由名称推导而不是抄写——并与引擎实际运行的 script 逐字节比较。这不是装饰：初稿按声明顺序
  压入参数，每个调用到达时参数都被旋转，注册步骤把这种旋转报告为缺失的备份所有者。帧中的地址是
  步骤命名的那个，因此针对插件的步骤会用插件的地址与其 manifest 重建，而不是账户的；场景未部署的
  目标会被拒绝，而不是回退到账户，因为静默回退会把错误的合约报告为返回类型不匹配。
- **形状。** 相同步骤、相同顺序、相同 id 与方法。丢失一个步骤的 dump 不能因为再没有东西可分歧而
  通过。
- **时间。** 每个调用都在场景为其声明的区块时间运行，且 dump 说明是哪一个。`Runtime.Time` 是持久化
  区块的时间戳，因此声明较晚时间的步骤会得到一个该时间的区块，并看到较晚交易会看到的相同存储。
  这正是使时间锁可度量的那个问题：冻结在单一瞬间的测试装置能表明窗口之前的调用拒绝，却永远不能
  表明窗口处的同一调用成功。
- **结束。** 每个调用结束在场景所说的位置，预期故障的调用以声明原因故障。二百二十八步中有四十二步
  是预期故障——尚未到期的时间锁、不存在的提议、永久的恢复——因此失败路径与成功路径一样被刻意度量。
  故障还可以固定一个 `detail`：reason 是目标 script 中止时的原因，detail 是主机在其下记录的内容，
  同时固定两者就是固定两个不同的层。只声明通用主机消息的场景不会说明它度量的是哪种拒绝。
- **返回。** 声明的返回类型从 manifest 读取，并用派发面相同的三值规则判定，从 `abi_dispatch` 加载
  而不是重述，因此“manifest 描述了返回之物”不会在两个地方被判两次。manifest 是步骤所调用合约的
  那一份。
- **值。** 场景声明的整数、布尔与数组长度就是引擎产生的那些，且每条声明的读取链接成立：三十八条
  链接逐字节把结果与参数联系起来。其中包括由纯函数派生到后续调用所注册身份的账户 id、写入后回读
  的备份所有者／验证器数据／元数据 URI、由声明区块时间打上的逃逸时间戳、被提议然后作为就任管理员
  回读的管理员，以及两个批量注册账户回读出该批量签名所用的同一个备份所有者。
- **模块。** 落在插件上的步骤与该插件比较：引擎部署的地址就是场景命名的地址，其部署字节哈希到场景
  指向的文件，在这里从磁盘读取而不是取自 dump。签名者也被比较，因为已部署合约的地址是 NEF、
  manifest 名称*与*部署签名者的函数，三者中两者匹配而没有第三者的说明不了什么。dump 报告而场景未
  声明的插件是失败，地址、字节或签名者移动的也是失败。这个问题存在，是因为 `AssertV3Verifier` 与
  `AssertV3Hook` 读取已部署 manifest 而不是源文件：准入检查是关于工件的主张，而工件主张需要工件
  问题。
- **冻结。** 预期故障的步骤不是任何后续步骤读取的对象，因为这个测试装置共用一个存储快照，且不回滚
  故障调用。在故障之上构建不是会恢复的场景；而是度量一条没有链会到达的状态。面拒绝它。

每次调用运行十六个变异，覆盖全部四个文件：字节不是场景的调用、结束在别处的调用、在另一时间运行的
调用、由另一账户签名的调用、原因不同的故障、场景未声明的值、不是写入值的值、缺失步骤、乱序 dump、
manifest 未描述的值、不是场景命名部署的部署、由另一场景产生的 dump、构建在故障上的步骤、部署在
另一地址的插件、由其他字节部署的插件，以及瞄准步骤未命名合约的调用。无法构建的变异计为失败而不是
缺席——缩小到仍然适配的自测会认证它没有检查的输入。其中一个此前因错误原因通过，并因此被发现：它用
`0x7777…` 重写签名者，而那恰好是第一步已有的签名者，所以它什么都没改，面正确报告无差异。它现在
选择一个该行不携带的值。

它在固定工件上度量到：四个文件上的 228 个调用，186 个停止，42 个以预期原因故障，228/228 个帧与

#### 账户之旁的插件

前两个文件只能度量本合约与自身及 VM 的对话。第三个限制是结构性的而不是时间性的：验证器方法体没有
验证器就无法运行，而准入检查读取已部署合约的 manifest 而不是源文件。前两个文件中的任何东西都无法
到达 `AssertV3Verifier`、`callVerifier`、`callHook`、`isModuleInstalled` 或任何待处理模块 getter，
因为到达它们需要在同一引擎中存在一个插件合约。

`scenarios/aa-account-plugins.json` 在账户旁边部署四个插件并调用它们。两个是相同 `MultiSigVerifier`
字节在两个部署签名者之下，这给了轮换一个可轮换的目标。两个 hook 是不同的合约，而两者都有正是重点：
`NeoDIDCredentialHook` 的 `ClearAccount` 清除自己的存储，而 `MultiHook` 的会无条件回调核心的
`clearHookDependencies`。这个构建的账户暴露了该回调，因此两条两阶段清理路径都完成：
`call-hook-a-confirmed` 与 `call-hook-b-confirmed` 各自在第一次调用记录待处理请求、第二次在时间锁
之后执行之后停止。保留这一对使回调绑定可见，而不是把它藏在一个插件后面。

执行的那些插件方法体是真实的。`call-verifier-confirmed` 在 VM 内运行 MultiSigVerifier 的
`clearAccount`，`call-hook-a-confirmed` 运行 NeoDIDCredentialHook 的，二者都在账户清除三道门之后：
插件的授权核心是本合约、`Runtime.CallingScriptHash` 是本合约，且账户表示调用方当前是它的验证器或
hook。

工件按哈希固定，其溯源被记录而非重新推导。`plugins/provenance.json` 命名编译器（`nccs 3.9.1`，
因为 NEF 头部命名了它，而其代码生成决定字节）、项目文件、喂给它的每个源文件，以及全部十二个工件的
sha256。`plugins/build-plugins.sh` 是记录的构建步骤：它拒绝针对不同编译器运行，且若其产生的任何
工件哈希与溯源文件记录不同则以非零退出。这正是主合约在 `contracts/bin/v3` 的既有地位——一个带记录
推导的固定输入，而不是任何运行会重新推导的东西——并且它不是插件正确的证明。

#### 账户之旁的调用方

第四种不可达性关乎*谁在调用*。平台 registrar 通道与市场托管都断言其调用方是账户记录过的合约：
`registerPlatformAccount` 与平台所有者轮换检查 `Runtime.CallingScriptHash == registrar`，而
`enterMarketEscrow`、`cancelMarketEscrow` 与 `settleMarketEscrow` 对照市场检查它。任何瞄准账户的
步骤都无法满足这一点，因为步骤的调用方是交易的入口脚本。

`scenarios/aa-account-registrar.json` 改为部署另一方，而不是插件。它安装的六个工件中有三个既不是
插件也不在被测之列：AAPlatformRegistrar 服务合约，以其自身管理员驱动，使其调用经 registrar 门到达
账户；一个带全权权限、让市场自己的调用能来自合约的转发器；以及一个 paymaster。全部六个都像插件
一样按哈希固定，回执比较每个的地址、字节与部署签名者——关于“谁调用了账户”的主张就是关于工件的主张，
因此它得到工件问题。

这到达了什么：registrar 按合约要求被提议并确认（七天、管理员见证），平台账户由 mock 注册，然后通过
`getAccountIdByProxy` 对照其代理 script 哈希回读，所有者轮换被提议、在窗口之前拒绝、取消、因无待
处理而再次拒绝、再次提议并由新所有者见证确认；托管由市场在三个挂单上开启，然后通过两个出口驱动
——所有者的时间锁强制取消与市场的取消及结算。这六个入口在账户内部执行，并由它们改变的状态作为
证据，而不是由落在它们上的步骤作证，这就是状态块把它们与步骤直接命名的 88 个分开计数的原因。还有
一个入口 `clearHookDependencies/1` 由插件回调到达：`MultiHook` 的 `clearAccount` 无条件回调核心，
因此即便没有步骤命名该入口，两阶段清理路径也会运行。

仍有十四个入口未被到达，并被声明为如此而不是被计入：

- `_deploy/2` 与 `_initialize/0` 在 manifest ABI 中且完全不能被调用。`System.Contract.Call` 在被
  调用者运行一条指令之前就拒绝任何以下划线开头的方法名——运行记录了主机自己的消息
  `Method name '_deploy' cannot start with underscore`。它们是平台的部署钩子。一个“覆盖”它们的
  场景将是在度量引擎的参数检查并称之为覆盖。
- 另有十二个入口当前没有场景驱动：账户冻结生命周期（`freezeAccount/1`、`unfreezeAccount/1`、
  `isAccountFrozen/1`）、依赖配置写入器（`setHookDependencies/2`、`setVerifierDependencies/2`、
  `clearVerifierDependencies/1`）、子 hook 转发器 `callHookChild/4`、模拟读取
  `simulateValidation/2`，以及读取 `describeAccount/1`、`getPlatformAccountBinding/1`、
  `isMarketService/1` 与 `isUserOpExecutionActive/0`。每一个都是普通的已授权入口，只是场景文件没有
  调用——这是覆盖率陈述，不是缺陷——门禁把它们计为未到达，而不是粉饰缺口。

`cancelPlatformRegistrar` 在当前工件中是一个成功的控制。在配置的时间锁处它删除待处理提议与时间锁，
并发出 32 字节的 `PlatformRegistrarCancelled` 事件。此前 34 字节的事件名已被修正，场景现在要求
`HALT`，而不是记录主机故障。

#### 每个窗口的另一侧

第二个文件的存在源于第一个文件的结构性限制。合约用延迟保护的一切——合约升级、管理员转移、逃逸
冷却、逃逸时间锁、批量所有者注册——都是与 `Runtime.Time` 的比较。一个声明的区块时间只能到达那些
比较的拒绝侧，因此第一个文件包含四个“尚未”形状的故障，且它们中没有一个在末端成功。那是把半条规则
度量了两次。

`scenarios/aa-account-windows.json` 为每一步声明一个时间：共九个，每个放在边界前一毫秒，然后恰好
放在边界处。四对是在两个不同时间以相同参数发起、结束不同的同一调用——管理员转移确认、针对冷却的
逃逸发起、针对时间锁的逃逸终结，以及在批量注册账户上把同一终结一路驱动到永久恢复。回执中没有其他
东西能产生那一对，因此门禁把“声明了不止一个区块时间，却没有结束方式依赖其一的调用”视为失败而不是
通过：一个被声明而未被度量的维度，就是回执否则会计为已覆盖的维度。

合约有两件事只有从成功一侧才可见，二者都是先弄错才发现的。`finalizeEscape(id, 0x0)` 与
`finalizeEscapeToOwner(id)` 不是同一操作：前者清除验证器与 hook 并把账户恢复到备份所有者模式，后者
还把它标记为永久仅所有者。本文件初稿期望在返回验证器的调用之后 `isOwnerOnlyRecovery` 为 true；引擎
说是 false，而随后一次 `finalizeEscapeToOwner` 报告 `Escape not initiated` 而不是
`Already recovered`。两个期望都对照引擎被改正，文件现在各驱动一个账户走一条路径。另一件是
`registerAccounts` 按账户接收验证器参数，这使两个 id 在同一个备份所有者下可区分——批量用 `01` 与
`02` 注册两个账户，并从两者回读同一个备份所有者。

它不做什么：四个文件合起来对 109 个入口中的 14 个什么也没说——`_deploy/2` 与 `_initialize/0`，引擎
根本拒绝通过 `System.Contract.Call` 调用，加上上文列出的十二个没有场景步骤驱动的操作入口——对这些
文件之外的参数值什么也没说，对同一状态上的第二次调用序列什么也没说。它也不能证明*选择*调用什么是
有意义的——一个只调用平凡 getter 的场景会满足上面每个问题，却什么值得知道的都没度量。门禁中的非空
地板（停止、故障、不同方法、读取链接、每个停止调用的形状检查、声明不止一个区块时间时的时间敏感对，
以及对声明模块的场景：一个部署地址、一个工件哈希、一个签名者与至少一个落在其上的步骤）给了它界，
但它们只是给界，并不移除。

`fullImplementationVerified` 保持 `false`。

## 仍然开放

- 语法未被证明。存在的是三个读取器——我们的两个与 Microsoft 的词法器——在实测语料上的一致，外加
  一个证明测试装置能看见差异的自测。我们两个读取器之间的一致不是关于 C# 的定理；与 C# 词法器的一致
  是度量，且其作用域限于泳道命名的片段。
- 编译器语义完全未被上述触动。字节身份说明编译器是确定性的、工件就是那个工件；它不说明
  `contracts/` 中的 C# 是否与其发出的操作码行为一致。VM 一侧由单独的 VM 泳道处理，而不是本泳道。
- 语料是泳道加载的固定源码，不是整个 `neo`。没有泳道读取的文件未被覆盖，且回执命名它使用的镜像，
  使这一点不会被误认。
- 扫描器读取语料拼出的字符集，有三种形状在其外：C# 11 原始字符串字面量（扫描器把 `"""` 读作一个
  空字符串后跟另一个字面量）、`U+` 转义标识符，以及运算符与单字符集合之外的任何字符，后者被*拒绝*
  而不是跳过。固定语料中没有一个出现——若出现一个，前端会在整个文件上与词法器不同，门禁会说出来，
  因为缺口就是 `KNOWN_FRONT_END_GAPS` 中的新文件名，而该列表为空。
- 仍有三个模块保留自己更窄的表——`gas_proofs`、`runtime_collection_source`、`runtime_source`——
  本页的面不度量它们的读取器。它们在 `sharedReader.privateTableModules` 中具名，因此范围限制在
  回执里而不是某人的记忆里，缩小该缺口是分开的工作。
- 预处理器以空符号集求值，这匹配一个什么都没有定义的词法器。若真实构建定义了 `VMPERF`，编译器看到
  的是该区域的另一分支。回执打印 `symbols: []`，使假设可见而不是隐含；定义了东西的构建需要在两侧
  都传入该集合。
- 短针面问两个读取器是否在同一位置以相同次数看到同一字符串。它不问泳道是否在正确的文件中查找：一个
  恰好出现一次但在错误文件中的针满足它，只有泳道自己的固定值抵挡这一点。它还只读取其解析的九个模块
  的投影函数，因此保存在别处的针在范围之外，而它跳过的八个管道函数打印在回执中而不是留给记忆。
- 足迹说引擎进入了哪些指令，而不是它们计算了什么。参数全为零，因此 107 个已派发调用中有 67 个以
  `FAULT` 结束；面比较指令身份，对值保持沉默。
- 边界面说引擎拒绝哪些调用，以及被接受的调用落在哪里。它不说合约*本应*自己拒绝形状错误的参数：
  94 个中有 7 个进入并正常回答，而那是否可辩护是那七个入口的属性，不是引擎的属性。回执计数它们
  （`boundaryTypeCompleted`），把判断留给读取该入口的人。它还只度量一个引擎版本，因此
  `shapeEnforcedAtBoundary: false` 是关于此处构建的 Neo 3.9.1 的事实。
- 场景层为它命名的 ABI 入口作答——另有 6 个通过已部署调用方到达并由其改变的状态作证——且只对四个
  文件中的序列作答。其余关于行为的每个问题——这些字面量之外的参数、同一值的第二次读取、真实链会
  回滚的故障之后的调用、无人写步骤的入口——都在它之外。剩下的 2 个不是靠写更多步骤修复的覆盖率
  问题：`_deploy/2` 与 `_initialize/0` 根本无法通过 `System.Contract.Call` 调用。
  `cancelPlatformRegistrar` 现在是一个成功的控制：它在时间锁处完成并发出
  `PlatformRegistrarCancelled`，该名称在 Neo 的 32 字节限制内。因此
  `ACTUAL_VM_APPLICATION_ENGINE_ABI_DISPATCH` 仍因义务而开放，不是因噪声而开放：缺失的是语义——
  返回形状不是行为——而面无法制造它。
- 插件工件是带记录推导的固定输入，不是证明。`provenance.json` 说明哪个编译器把哪些源码变成哪些字节，
  而 `build-plugins.sh` 重新推导它们；两者都不说明插件正确、可安全部署，或一条活链会运行什么。场景
  度量账户准入并调用了固定插件，包括 `NeoDIDCredentialHook` 与 `MultiHook` 两条已确认的两阶段清理
  路径。那些是工件级控制，不是任意插件方法体正确或活性的证明。
- 时间是声明的，不是观察到的。一对边界表明测试装置在两次调用之间移动了，它不表明链会如此：没有链、
  没有共识时间戳、没有漂移。这一对度量的是合约在场景命名的两个值处执行的比较。
- 场景测试装置在各步骤之间共用一个存储快照，且不回滚故障调用。面拒绝在声明故障之上构建，这是要紧
  的情形，但场景*没有*预测到的故障只在事后由结束检查发现。一个建模回滚的有状态测试装置将是另一件
  更大得多的设备。
- 足迹所对照的静态模型，就是入口点清单发布的同一个结构图。因此包含性只在该图上、每个入口点一条
  路径上测试其健全性，而不是完整性：634 个可达成员从未被进入，而这里没有任何东西说明该图列出了
  另一组参数可能到达的一切。
- `implementationVerified` 与 `fullImplementationVerified` 保持 `false`。

在门禁内部，语料是被发现而不是被提供的：

```python
corpus_roots = sorted(str(path) for path in output.glob('*/source') if path.is_dir())
frontend_receipt = correspondence.correspond(stage, corpus_roots)
require(correspondence.agrees(frontend_receipt), 'source frontend correspondence mismatch: ...')
```

空语料会被拒绝，因此一次没有找到任何 `source` 目录的运行不能被报告为一致。
