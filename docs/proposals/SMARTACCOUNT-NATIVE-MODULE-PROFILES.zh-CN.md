# 原生 SmartAccount 模块配置档

> 中文版本与 `docs/proposals/SMARTACCOUNT-NATIVE-MODULE-PROFILES.md` 同构。若两者冲突，以英文版本为准。

## 兼容性边界

已部署合约配置档与原生 SmartAccount 配置档是不同的构建目标。当前原生工件要求 `native-v2` 与 `extra.smartAccount.abiVersion = 2`；ABI 1 工件不兼容。身份派生仍为版本 1。每个账户自有模块键都是 `0xA2 || policyPrefix || accountIdLE20 || authorityEpochLE64 || suffix`，其中 policyPrefix 为一个字节。纪元在每次访问时取自 safe 原生 getter，且必须落在 UInt64 范围内；不可用或非法的读取失败关闭。不存在旧命名空间回退。这包括密钥、授权、冷却、支出、配置、子级名单与瞬态快照。恢复会改变纪元并撤销根与依赖，不调用旧模块回调，使旧字节不可达。重新安装模块会从空的当前代次状态开始。普通配置保留存储纪元并推进 configurationNonce。

既有验证器工件声明 `Any` 回调参数并使用 `canConfigureVerifier` / `canExecuteVerifier`；原生准入要求精确的 `Array` 参数与已认证的 `hasModuleContext` 阶段。既有钩子权威查询同样面向已部署合约配置档。通过旧版部署测试并不确立原生兼容性。

原生构建不得放宽原生合约 ABI、模拟托管见证、使用只认哈希的调用方捷径，或回退到旧版授权。原生合约身份由原生配置档固定。配置、清理、校验、preExecute 与 postExecute 各自需要其自己的精确账户、模块角色与调用阶段授权。独立的模块管理绝不替代这一按账户作用域的授权。

## 初始配置档

原生构建复用既有的 NeoNativeVerifier 签名方/阈值策略与 WhitelistHook 存储/许可名单策略。`SMARTACCOUNT_NATIVE` 只选择原生权威与精确回调签名；普通构建保持其既有 ABI 与权威行为。两种配置档都保留完整生命周期、适用情况下的签名方域发现、带时间锁的模块管理与账户清理。它们不是仅用于测试的“接受一切”验证器。

- NeoNativeVerifier：类型精确的 Array 操作、真实交易见证阈值、互不重复的非零签名方身份，以及原生校验/postExecute 授权。配置能力：`setConfig`。
- WhitelistHook：原生 preExecute/postExecute 授权、默认拒绝的目标查询，以及按账户作用域的清理。配置能力：`setWhitelist`。

原生 NeoNativeVerifier 在同一权威纪元下，以策略前缀 `0x03` 按顺序把确定性签名方域存为拼接的 32 字节值，并与其签名方配置原子写入。safe getter 读取新鲜状态，要求在既有的十个签名方模块上限内、长度为 32 字节的非空整数倍，并返回相互独立的 ByteString。清理会删除该值。公开的 `getConfig` 形状仍为 `[signers, threshold]`，每次校验与选定的后置回调仍检查真实见证法定人数。MultiSig 聚合域上限另为三。这些存储的身份不是操作批准，也不取代任何签名或见证检查。

已配置的交易见证授权原生验证器。它们不是自定义的操作签名格式。下文的 SessionKey 配置档增加了一个独立的操作签名适配器；任意证明/证明插件仍是独立工作。

当前描述符还包含 SessionKeyVerifier、DailyLimitHook、TokenRestrictedHook 与 MultiSigVerifier。前三个配置档的要求见下文；组合配置档及其瞬态批准回执回调定义于 `docs/proposals/SMARTACCOUNT-NATIVE-MULTISIG.md`。

本仓库的原生构建描述符目前恰好包含六个受支持的 ABI 2 工件：NeoNativeVerifier、WhitelistHook、SessionKeyVerifier、DailyLimitHook、TokenRestrictedHook 与 MultiSigVerifier。MultiSigVerifier 是原生构建实现的唯一组合配置档。`MultiHook` 仍是普通合约组合模块：它没有原生项目、描述符条目、打包后的 ABI 2 工件或原生符合性回执。其普通 `supportsComposition()` 标记与旧构建工件并不使其成为原生模块：普通工件无法通过原生 ABI 与配置档检查。构建描述符不是工件哈希的共识白名单。核心可以准入另一个满足其完整接口、元数据、代码身份与发现规则（包括其受支持的钩子组合接口）的原生实现；这并不确立该模块的行为或资源充足性。新增仓库支持的原生 MultiHook 需要单独的原生实现、描述符条目、打包测试与私有链验证。

## 工件构造与安全

编译器输出不会被手工修改以掩盖 ABI 不匹配。原生项目使用源码级的 Array 回调声明。当前编译器只支持字符串值的清单扩展字段，因此原生打包阶段从已入库描述符与单一参数来源添加结构化的 `extra.smartAccount.configurationMethods`、`compositeVerifier`、`compositeProfile` 与精确配置档参数摘要。组合根通过 `extra.smartAccount.compositeProfile` 按名称声明其配置档；链码在准入时绝不硬编码诸如 `MultiSigVerifier` 或 `MultiHook` 之类的模块合约名。它必须拒绝缺失、重复、safe、保留或账户作用域错误的 ABI 方法。原始编译器字节与打包后的清单字节、描述符、链接的源码文件、编译器身份与打包配方都必须被哈希。已部署代码身份使用打包后的清单。不允许不透明的 NEF 重写。全新重放必须复现每个原生工件的字节；普通配置档工件保持单独校验。

M-5 输出目录约定：`contracts/build/` 是普通轨构建输出目录，专门保留给普通配置档工件（其字节固定值位于 `tests/localchain/expected-deployed.json`）。原生轨打包工件——NEF 加上携带 `extra.smartAccount` 声明的打包清单——只由隔离的原生模块构建生成到其独立的打包输出目录，且不得被复制进 `contracts/build/`。因此部署加载器绝不会把同一源码的普通配置档构建误当作打包的原生 v2 模块，原生打包失败也绝不会被停在预期路径上的普通工件掩盖。

描述符必须是非空对象，含简单的工件名与项目名、显式角色、非空的唯一配置名数组，以及显式的 `compositeProfile` 声明（叶子模块为空，组合根为配置档名；组合验证器必须始终声明其配置档）。输入必须留在合约树内；符号链接与别名到既有输出都会被拒绝。构建或打包操作失败必须留下失败回执，绝不继承先前调用的成功结果。空描述符与格式错误的能力类型必须在编译前失败。

已安装的编译器不会把项目的 `DefineConstants` 值传播给其合约解析器。因此原生配方只把显式链接的源码复制进一次性项目，并为每个文件加上标准 C# `#define SMARTACCOUNT_NATIVE` 指令。原源码绝不被改写。原始源码与预处理后源码的哈希都会被记录。原生标记与精确 Array ABI 在编译后检查，因此静默编译旧分支是错误的，而不是可接受的原生工件。

## 必需的验证

先在原生合约上复现既有验证器 ABI 的被拒行为。然后在一次性 NeoExpress 链上部署真实原生工件，并回读其 NEF 与打包清单。测试登记、延迟账户配置、真实阈值签名、缺失/错误见证、许可名单拒绝、直接配置与阶段混淆拒绝、跨账户隔离、替换时的清理、FAULT 时 nonce 保持，以及事件/状态回读。拒绝之后要包含正向对照。不要复用钱包密钥、链或远程端点；回执不含私钥或主机路径。

新的原生工件不是已部署旧合约的升级。迁移需要显式重新部署与原生账户绑定，而不是假定的 ABI 或存储升级。本工作不含任何公开部署。原生模块 gas 由协议限定；成功的示例不是完整的成本画像，也不是任意插件证明或编译器精化。

## 形式化对应边界

`NativeInvocation.v` 把精确的 SmartAccount 原生合约身份检查与所需的已认证调用授权建模为一个合取。配置错误的原生合约或缺失授权会被拒绝；配置匹配且有授权的原生合约仍可达。

既有的帧、阶段、角色与账户定理适用于该抽象授权谓词。共享权威源码与全部六个选定模块源码在评审后由形式化门禁钉住。钉住值能检测源码漂移；它们不证明 C# 预处理、编译器正确性、原生回调精化或密码学。

## 会话密钥原生配置档

SessionKeyVerifier 使用相同的六字段 Array ABI，以及精确的原生校验、postExecute、配置与清理授权。旧式的直接托管见证配置捷径不是原生授权路径。声明的原生配置能力为 `setSessionKey` 与 `clearSessionKey`。

P-256 签名输入是原生授权域字节序列，后接对签名字段为空的规范操作执行 `StdLib.Serialize` 的结果。`getPayload` 返回该原像，而不是其摘要。它的单一 SHA-256 哈希必须等于 `SmartAccount.getOperationDigest`；CryptoLib 的 secp256r1SHA256 验证器恰好对原像哈希一次。把已哈希的摘要喂给内部会再哈希的 API 不属于本配置档。签名为定宽 64 字节 `r || s`；JSON 编码、旧版验证器特有载荷与 DER 签名都被拒绝。

原生 Session 配置把规范签名方域以策略前缀 `0x05` 单独存储，与其密钥处于同一权威纪元命名空间。该值为 `NativeScript(CreateStandardAccount(publicKey))`，并与该密钥原子写入。它是确定性配置数据，不是签名/批准缓存。撤销与清理会删除两个值。域 getter 重新读取当前纪元，并拒绝缺失或格式错误的域；不存在回退。原生模块必须全新部署并配置。两种配置档都保留既有的五字段 `getSessionKey` 结果；旧版构建不写原生域前缀，并保持其各自的域语义。原生配置先通过原生 `canonicalP256PublicKey` 查询解码 33 字节压缩或 65 字节未压缩的 secp256r1 点，该查询校验整点往返相等性并在写入前拒绝非法点。仅使用通用的标准账户 syscall 无法为未压缩点确立这一性质。它存储规范的压缩点；因此两种编码派生出相同的标准账户身份。

原生最后使用时间戳单独存放在前缀 `0x06` 下。配置把规范的、无符号 UInt64 Neo 整数初始化为零；不可变的元数据记录保持 `[createdAt, 0, description]`。公开元数据 getter 重新叠加该时间戳并保留其原有三字段结果。执行后只校验并更新时间戳，避免对描述反复序列化与存储计费。缺失、为负、溢出或非规范的时间戳字节失败关闭。撤销与清理会移除域键与时间戳键；普通撤销只保留轮换冷却。同一回调内的密钥复用从一份重新派生的原生纪元密钥开始，并且只覆盖固定的原生/存储调用，绝不覆盖任意子级回调或后续操作。

公开的 `getPayload` 查询会对照规范原生 getter 校验其摘要，并拒绝非法操作形态。在已认证的原生校验回调期间，模块直接由新鲜的原生授权域与规范未签名操作构造同一原像，而不重复等效的摘要查询。独立字节向量、编译模块的载荷查询与已签名操作必须证明其相等。这不会移除任何签名验证或阶段/账户/纪元检查。

会话过期在 Application 中使用持久化区块时间戳，在 Verification 中使用最新的持久化账本区块时间戳，与原生合约一致。在没有持久化区块的真实见证 Verification 引擎中，`System.Runtime.GetTime` 不可用。在那里直接使用会拒绝本来有效的代理见证。时间来源由触发选择，绝不由调用方选择。

原生限额会话被限定为精确的 NEP-17 转账形态：四个参数、以账户资产地址为来源、非零 Hash160 接收方，以及非负的精确 Integer 金额。校验检查累计上限；postExecute 要求精确的 Boolean true 结果才记账扣减。业务结果为 false 会使操作致命失败，并保留 nonce、支出状态与资产余额。目标本身必须实现所声明的代币语义；任意不诚实合约的外部效果无法从其方法名推断。未限额或通配会话仍明确为未限额。

清理在清理授权下移除密钥、元数据、支出与轮换状态。普通撤销保留轮换冷却；替换生效密钥不会重置累计支出。核心配置延迟仍然适用。若替换把正上限降到低于累计支出，每一次限额操作都必须被拒绝，包括零金额转账。零金额在恰好到达上限时可以接受，但绝不绕过已经超出的上限。普通撤销会清除累计支出，作为托管方显式授权的策略重置；随后的延迟授权会开始新的额度。未经撤销的轮换不属于此类重置。ABI 2 操作签名同时绑定 authorityEpoch 与 configurationNonce，因此恢复更早的密钥无法恢复更早配置下的签名。即时遏制需要已配置的恢复权威与原生冻结；不存在隐藏的直接托管撤销捷径。被冻结的账户不能使用通用配置。延迟与恢复依赖是运行限制，而不是即时会话撤销的主张。

验证矩阵必须使用真实生成的 P-256 密钥、独立的交易支付方，以及经由账户代理的真实原生 GAS 转账。它必须把独立序列化的签名输入与摘要和两个原生查询比对，拒绝错误的账户/网络/核心、被篡改的参数、错误签名、已过期密钥与超额支出，并回读持久化的回滚与清理结果。密码学原语与完整编译器精化仍是独立的证明。见证准入是与持久化 Application 执行不同的门禁：错误签名与过期会话的代理见证必须被 `sendrawtransaction` 拒绝，且两个账户的观测存储、nonce 与余额保持不变。准入拒绝绝不能被计作持久化 FAULT。同一规范代理脚本还必须准入一笔合法签名转账。生命周期矩阵还要替换已用密钥、验证支出保留与旧密钥被拒、恰好花掉剩余额度、把上限降到低于已花额、再恢复到精确边界、撤销密钥，并在协议延迟后授予新额度。它要比较全部六个裸存储前缀，包括普通撤销冷却的保留与其被账户清理移除。

`NativeSessionPolicy.v` 建模限额会话关于上下文、签名接受、目标/方法作用域、过期与精确转账形态的合取。它证明扣减边界、对每个缺失条件的拒绝、精确的成功扣减，以及目标失败或操作被拒时支出不变。这些布尔值是运行时提供的抽象事实，不是 P-256 或解析的证明。其正向对照与条件移除变异必须通过形式化门禁。时钟抽象单独证明：见证校验选择持久化时间戳（不可用时失败关闭），而 Application 选择持久化时间戳。该选择证明并不确立账本 syscall 或触发实现精化了模型。生命周期抽象还区分密钥替换（支出保留、轮换时间戳刷新）、普通撤销（密钥与支出清除、时间戳保留）与账户清理（时间戳不保留）。冷却拒绝与零金额上限边界需要独立证明与变异对照。原生合约的延迟配置仍是额外的门禁，而不是模块冷却规则的替代。

### 未限额作用域与密钥复用

零支出上限会禁用会话的转账特定形态、Boolean 成功与累计扣减检查。它不会禁用目标身份、方法作用域、签名、过期、账户状态或 nonce 检查。通配方法允许在唯一配置目标上使用不同方法；它不是通配目标。正上限在配置方法不是恰好 `transfer` 时无效。授权事件必须暴露精确作用域与其未限额标志，使运营者不会把零误认为零额度。

对于已准入的未限额操作，目标以 Boolean false 停机（HALT）仍算完成的操作：nonce 与最后使用元数据会推进，而会话支出不变。目标 FAULT 会回滚该操作。读方法与移动值的方法都必须在显式通配授权下演练，并配以独立的错误目标与精确方法负向对照。私有矩阵必须包含一笔真实的整额 GAS 转账以展示该暴露面，而不是仅从事件推断。

ABI 2 操作签名绑定账户当前的 authorityEpoch 与 configurationNonce。执行入口点还在未签名交易脚本中携带两个期望计数器；这对原生交易见证验证器与托管回退是强制的，因为它们的证据否则并不承诺操作域。替换、撤销或重新授予同一密钥都会推进 configurationNonce；任何此类迁移之前保留且未消耗的签名在重新授权后必须仍被拒绝。恢复还会推进 authorityEpoch，并使模块先前的密钥/支出/冷却状态不可达。私有矩阵必须在这些迁移之间保留完全相同的签名字节并验证其被拒；在新计数器下重新签名的操作提供正向对照。已消耗的操作还会因其目标 nonce 被拒绝。

`NativeSessionScope.v` 保留一个叶子策略反例：若签名/域谓词保持不变，恢复密钥可以复活签名。这是历史 ABI 1 风险与显式抽象边界，而不是 ABI 2 端到端行为。`NativeAuthorityEpoch.v` 提供互补的状态迁移与域计数器义务。两个模型都不证明密码学、字节级密钥编码、VM，或它们与已部署工件的组合。运行时验证必须比较确切的带标签裸存储与原生/域回读。历史 ABI 1 回执不确立 ABI 2 兼容性。

## 每日限额原生钩子配置档

DailyLimitHook 只准入 `setDailyLimit` 作为其账户配置能力。执行前、执行后与清理各自需要独立的原生钩子授权。余额属于 `getAccountAddress(accountId)`，而不是账户标识符。原生转账预检要求精确的四参数形态、以已登记资产地址为来源，以及正的精确 Integer 金额。

权威计量是每个已配置代币的观测净流出，即使目标返回 Boolean false。返回 false 并不证明目标没有写入。每个余额必须是精确的非负 Integer；缺失快照与查询失败都会被拒绝。已完成的操作会移除全部快照；FAULT 会回滚 nonce、代币写入、记账与快照。这是净流出记账，不是对总中间流动或任意代币 `balanceOf` 实现诚实性的主张。

固定窗口从首次记录的流出开始，持续 86,400,000 毫秒。其后的流出不会移动该锚点。在边界处，下一次流出开启新窗口。滚动窗口保留时间戳大于或等于当前时间减去该时长的记录；下端点包含在内。既有的五十条活动记录上限失败关闭，而不是丢弃活动支出。移除某代币限额会清除其配置、固定计数器、历史与余额快照。账户清理会清除全部六个策略前缀。修改限额仍受原生配置延迟约束。

私有验证必须使用真实原生 GAS 余额与已签名代理见证，覆盖 false 返回、预检失败、同窗口转账、固定窗口重置、滚动累计/过期、直接阶段拒绝、跨账户隔离，以及清理后的完整存储前缀枚举。成功的示例并不证明任意已配置代币集合能装进回调 gas 预算。

### 对抗性流出与饱和验证

用于私有验证的诊断代币刻意不是符合规范的 NEP-17 实现：`moveThenFalse` 在精确的来源见证检查之后改动自身余额，然后返回 Boolean false。已配置的每日策略必须对观测到的流出计费，在 postExecute 中拒绝超额，并在拒绝时回滚双方余额、nonce 与策略存储。该夹具永远不是生产模块，也不替代真实 GAS 转账测试。其两次干净构建与已部署 NEF/清单必须逐字节比对。

原生授权属于确切的生效目标帧，而不是任意后代。因此转发 GAS 转账的诊断目标不得继承代理见证，即使交易的 WitnessRules 允许该调用方。私有测试必须断言这一拒绝，而不是为让示例成立而放宽原生权威。目标自身的计量余额与嵌套的原生 GAS 授权是彼此独立的主张。

滚动窗口容量必须在单个已配置 GAS 代币、每钩子回调预算仍为 2.5 GAS 的前提下，用五十条活动记录演练。第五十一次正流出必须以策略的历史容量错误失败，而不是更早的 gas 耗尽。过期之后，新流出必须成功并清除全部过期记录。记录标识符保持单调递增；不得为通过预算测试而丢弃或覆盖任何活动记录。回执必须区分已消耗 gas 与交易的费用额度。

单遍滚动历史扫描必须精确计算包含式时间谓词保留记录的和与数量。移除过期记录必须保留这两个结果以及每一条活动记录。抽象扫描等价性与追加容量证明与实测 NeoVM 回调成本相分离；二者都不证明任意代币查询成本或编译器对应关系。

### 非法余额观测

原生计量只接受来自每次代币查询的精确非负 VM Integer。负整数、ByteString、Boolean、Null 与 Array 结果都不会被强制转换为余额。查询故障与继承回调预算耗尽会中止操作。若目标先改余额再改变其查询行为，则在执行后查询失败时不得提交这些写入。测试必须比较裸代币存储，而不是把同一敌意 `balanceOf` 结果当作其判定依据。

私有诊断夹具可以在其部署支付方的见证下，为单个资产地址选择这些行为。这是测试管理，不是 SmartAccount 配置权威。测试在执行前与执行后两个阶段演练每种行为，要求在 FAULT 之后账户/接收方存储、nonce 与策略状态不变，并包含成功对照。对消耗 gas 的代币限额的延迟移除必须能够在不查询该代币的情况下完成，随后一笔 GAS 操作成功。这并不保证代币诚实，也不保证可从任意已配置策略中即时恢复。

## 受限代币原生钩子配置档

TokenRestrictedHook 只准入 `setRestrictedToken` 作为账户配置能力。配置、执行前、执行后与清理各自需要其独立的原生授权与固定的原生合约身份。其资产地址是已登记代理，而不是账户标识符。要求非零的合法 Hash160 代币身份；移除不会调用该代币。

每个已配置代币在执行前后都被观测。直接调用受限代币被禁止，包括只读方法。间接目标只有在没有任何受限代币的观测余额减少时才被允许，无论该目标返回 true、false 还是其他值。流入与净变动为零不属于流出。该策略不计量总中间流动，也不确立任意代币 `balanceOf` 的诚实性。

余额答复必须是精确的非负 VM Integer。缺失快照、非法答复、查询故障与查询预算耗尽都会中止操作。成功的执行后检查会删除全部快照；FAULT 会回滚目标的写入、nonce 与快照。移除某项限制会删除该代币的配置与快照。账户清理会删除两个按账户作用域的前缀。既有的每钩子回调预算不会被提高。不假定任意代币集合的成本能装进这些预算；移除故障代币仍是延迟的托管操作，且不查询该代币。

私有验证必须演练直接拒绝、结果分别为 true 与 false 的间接流出、净额为零与流入对照、两个阶段的非法查询、真实 GAS 转账、延迟移除与完整清理。仅用于测试的代币可以允许显式配置的路由器在无代理见证的情况下移动其自身余额，以模拟已有的代币侧委托。这既不是继承的原生见证权威，也不是生产 NEP-17 实现。运行时判定必须比较裸代币存储，而不是相信其敌意查询。两个诊断合约与该钩子都需要独立构建与完整的已部署 NEF/清单回读。旧版钩子配置档仍是单独的构建；原生专用守卫不得静默改变其工件。
