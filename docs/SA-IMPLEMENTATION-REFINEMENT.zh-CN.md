# custom 合约实现的精化

> 中文版本与 `docs/SA-IMPLEMENTATION-REFINEMENT.md` 同构。若两者冲突，以英文版本为准。

## 验收目标

目标是 custom `SmartAccount` 源码及其逐字节对应的已编译 NEF / manifest，包含全部公开
入口点以及它们可达的 helper。要求的结果是：从类型化 C# 操作到已解码 NeoVM 执行的语义保持，
并在此之上保持custom 模型中已经证明过的协议性质。手写模型的通过、哈希一致、编译器构建成功、
trace 采样或差分测试，都无法提供这条定理。

既有custom 候选验收在其已记录的作用域内仍然有效。在下列要求各自具备独立检查过的证书之前，
完整实现精化仍属未验证。不得为了让某道证明门禁通过而修改生产合约行为、编译器固定值、
公开部署或原始用户改动。

## 证明架构

1. **具体输入。** 解码真实的 NEF 容器与 manifest；保留原始字节、校验和、token、每一条指令
   边界与 ABI 偏移。按精确的类型、引用、常量和条件符号解析被选中的 C# 编译单元。源码位置
   与编译器调试数据只是定位义务的提示，不是"翻译正确"的证明。
2. **源码语义。** 为每一种受支持的类型化操作给出可执行的形语义。规定求值顺序、受检与
   非受检整数行为、`BigInteger`、null、引用、别名、数组、异常与调用。无法识别的操作必须
   被拒绝，而不是翻译成一个无约束的值或空操作。原生 / 框架调用需要显式的效果契约。
   源码方言必须在检查目标之前固定下来。尤其是：CLR `BigInteger` 运算无界，而 NeoVM 整数
   有带符号的 32 字节上限。在受限输入域上的保持定理必须声明该输入域，并另行证明真实入口
   守卫能够建立它。字符串编码 / 长度以及 CLR 与 VM 的异常行为同样需要显式语义；目标行为
   不能事后重新定义源码。
3. **目标语义。** 解释具体解码出的指令操作数、栈值、局部变量、静态字段、控制流与调用帧。
   声明所选 NeoVM 施加的限制，包括整数宽度、栈深度与 gas。故障、通知、存储与外部调用都是
   可观察行为。
4. **翻译证书。** 证明源码状态与目标状态之间的模拟关系。直线表达式的证书只对其精确区域
   有用。整方法需要每个分支与全部可达 helper；循环需要归纳不变式并处理终止或发散，而不是
   把有限展开报告为通用证明。
5. **ApplicationEngine 边界。** 把 syscall / 原生调用规约关联到固定的运行时实现。见证、
   存储序列化、嵌套调用、重入、gas 耗尽与交易回滚都不能用"无条件成功"假设替代。密码学
   假设与宿主服务必须显式列入可信计算基。
6. **组合与覆盖。** 只有当一个公开方法的证书、依赖与环境义务全部被消解时，它才算已验证。
   在 `implementationVerified` 可以变为 true 之前，所有 manifest 条目、初始化路径与可达
   指令都必须被清点。

针对具体工件的翻译验证避免了"为 NCCS 接受的每个程序都要求一条定理"，但它仍然要求对完整
的选定工件提供受检语义与证书。这遵循 [CompCert 手册](https://compcert.org/man/manual001.html)
中的语义保持区分与它的[研究目标](https://compcert.org/research.html)。具体目标是固定的
[NeoVM 实现](https://github.com/neo-project/neo-vm)，而不是一个操作码名字相似的无关栈机模型。

## 分层证明作用域

报销相关工作把证据分为下列几层。某一行中的证书不能消解另一行的义务；共享的导入声明不得
相加，仿佛每份回执都包含互不相交的证明。

| 作用域 | 被检查的陈述与边界 |
| --- | --- |
| 协议模型 | `formal/verify.py` 检查所声明的custom / 原生抽象。其模型回执不建立源码到 NEF 的精化。 |
| 算术区域 | `prove.py` 把原始计费指令绑定到带符号 256 位参考算术与 `CustomSponsorship.charge`。其作用域仍是局部区域。 |
| [数值强制转换](SA-METHOD-REFINEMENT.md#numeric-coercion-refinement) | 建模 GetInteger 解码及其值关系，包括 Boolean 与 ByteString。这不证明 ABI 准入或实际运行时对应关系。 |
| [预留算术](SA-METHOD-REFINEMENT.md#reservation-arithmetic-refinement) | 增加正性、可表示的预留更新与协议费用上界。它记录了零费用情形与无界算术之间的溢出分歧。 |
| [完整 helper 参考精化](SA-METHOD-REFINEMENT.md#complete-reimbursement-helper-reference-refinement) | 在声明的输入与环境契约下，把完整类型化源码投影与一个字节解码参考 VM 相比较，对象是 `CapReimbursementToActualCost`。它不认证 ApplicationEngine 或公开入口点。 |

[源码投影](SA-METHOD-REFINEMENT.md#full-helper-source-projection)记录了哪些类型化操作与语义元数据被解释。
[方法清单](SA-METHOD-REFINEMENT.md#whole-helper-refinement-inventory)清点了全部 helper
指令与独立的静态初始化；仅结构覆盖不是语义证明。
[运行时检查](SA-METHOD-REFINEMENT.md#complete-reimbursement-helper-runtime-checks)在固定引擎中执行
原始 helper，并区分有效输入、畸形记录、待定存储与外层交易回滚。这些检查提供有限的运行时
证据，独立于通用参考定理。

## Neo 合约方言与对象身份

完整的 helper 源码解释是一种被声明的 **Neo 框架合约方言**，不是任意 CLR 对象执行的解释器。
ByteString 与 UInt256 表示不可变字节值；该解释中的哈希相等比较的是它们的内容。持有可变
预留记录的 Array / Struct 保留堆身份与别名，因此经由栈引用的写入会更新仍被某个局部变量
持有的那个对象。序列化观察该对象，而反序列化从已存储内容构造一个新对象。这些是不同的
身份规则，不是一条笼统的值拷贝规则。

两个分别分配的对象之间的 CLR 引用比较，并不能自动满足按字节值相等的契约。导出某个操作的
类型或符号，同样不能证明编译器按本方言降低它。框架 / 编译器对应关系、对同一交易的重复
GetScriptContainer 读取、静态初始化以及原生编解码行为，仍是被命名的义务。回执必须保留
这些义务，而不是把它的方言定理呈现为一般 .NET 行为的保持。

[报销策略](SECURITY_MODEL.md)要求每个custom 核心在每个交易内只有一个预留上限。helper 参考
定理假设：交易哈希稳定为 32 字节、带符号 64 位费用非负，且要么没有账本，要么账本形式良好
（两个字段、32 字节哈希、非负且可表示的预留）。链级组合必须建立：可达的持久化记录满足
该不变式，且相同哈希字节在多次调用之间标识同一交易。策略本身不证明这些编解码与身份契约。
外部提供的畸形存储不得被当作已准入的可达状态，也不得被证明 oracle 静默修复。
[原生 profile 草案](proposals/SMARTACCOUNT-NATIVE-PROFILE-DRAFT.md)设置
`nativeSponsorship: false`；本custom 报销证明不是原生赞助标准，也不是激活声明。

## 证据与错误行为

精化门禁必须区分输入清单、结构校验、有界执行、通用语义证明与完整实现验收。它记录精确的
源码、NEF、manifest、语义模型、证书与工具身份。证明输出必须来自真实的证明内核调用，且
不得带被准入的声明或无法解释的公理。

畸形容器、非规范长度、无效 ABI 偏移、截断操作数、未知操作码、无效分支目标、缺失源码映射、
不受支持的类型化操作、未覆盖的方法以及过期证书，都是显式错误或开放的证明义务。它们都不会
被静默跳过。当任一必需义务仍未关闭时，请求完整精化的调用方会得到失败退出状态；仅清单模式
的运行不得声称实现 GO。

否定控制必须在保持输入形式良好的前提下改变源码或字节码语义：算术运算符与操作数、比较方向、
分支目标、见证守卫、写入顺序、返回值与回滚。其他控制覆盖被删除的 ABI 条目、缺失依赖以及
源码 / NEF 不匹配的组合。只拒绝非法语法或哈希变化，不能证明语义证书能发现错误编译。

## 资源与维护要求

清单解码应当与工件大小成线性关系。证明搜索有显式超时，并在失败时保留诊断。缺少工具时
失败关闭。生成的证明在隔离的临时目录中运行，且从不更新它自己的可信期望结果。新增指令或
C# 操作只产生新义务，不会自动增加已证明覆盖。

既有的 `formal/verify.py` 模型门禁与历史回执仍是独立的证据层。新的精化工作位于
`formal/refinement/` 之下；其报告必须准确说明哪些语义链已经建立。本验证工具不涉及部署
迁移。将来合约或编译器的改动，要求针对其新字节提供新证书。

## 运行实现门禁

在仓库根目录、并具备经审计的 NCCS 安装、.NET SDK 与 Rocq 的前提下：

```sh
python3 formal/refinement/verify.py --output-dir /tmp/sa-refinement-evidence
```

输出目录必须是新目录或空目录。运行器重建导出器，用扩展调试信息重新编译一份隔离的源码副本，
要求 NEF 输出逐字节一致，导出类型化源码与完整指令 / ABI 清单，运行证明内核，并在验证之后
重新检查输入。编译输入集在导出前、导出后与证明后各检查一次；新增的源码或构建文件与改动
过的文件一样会使门禁失败。证明模板计入验证工具输入哈希。

默认情况下，运行器请求全部四条精化证明作用域：算术、数值强制转换、预留算术与完整 helper
参考精化。它保留 `inventory.json`、`proof.json`、`numeric-proof.json`、
`reservation-proof.json`、`method-proof.json`、`method-inventory.json`、工具日志
与 `result.json`。每份回执都有自己的作用域与精确输入身份。带日期的整合报告
`reports/sa-method-refinement-20261013.md`（本检出中不包含）保留了
当时的最终回执及其逐作用域输入身份。它记录了哪些作用域是一起通过的；不同批次运行的
历史计数不能替代那份证据。

退出码 `0` 表示所请求的作用域通过；`1` 表示输入 / 工具 / 证明失败；`2` 表示所请求的
部分证明通过，但完整实现精化仍未关闭。`--allow-partial` 会接受这一已声明的部分作用域并
返回 `0`，但报告仍记录 `implementationVerified: false` 与全部未证明的公开入口点。它不得
被用作完整精化的发布命令。

若要只复现早期的算术区域作用域，请使用另一个空目录并显式选择：

```sh
python3 formal/refinement/verify.py --arithmetic-only --allow-partial \
  --output-dir /tmp/sa-refinement-arithmetic-evidence
```

该兼容命令省略了三条较新的证明作用域，不能替代默认门禁。缺少工具、不受支持的源码操作或
证明失败，在两种模式下都失败关闭；`--allow-partial` 不会绕过它们。
